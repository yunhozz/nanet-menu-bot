## 확정된 선택

사용자가 선택한 사항은 다음과 같습니다.

- 중복 방지 우선
- 최소 인스턴스 1개 유지 및 배포 후 유휴 비용 수용
- 새 브랜치에서 로컬 소스 보완
- 운영 배포 제외

예약 함수에 `min_instances=1`을 추가하고 기존 `max_instances=1`, `concurrency=1`, `retry_count=0`, 평일 10:00 `Asia/Seoul` 예약을 유지합니다.

**Scheduler 전체 재시도는 추가하지 않습니다.** 최소 인스턴스 유지는 인스턴스 부재 위험을 줄일 뿐이며, 이후에도 429가 발생하면 해당 예약 실행이 유실될 수 있습니다. 플랫폼 429를 안전하게 자동 재시도하는 설계는 이번 범위에 없습니다.

## 동작 설계

### 준비 단계와 전송 단계

공용 `app.run`에서 다음 경계를 명시합니다.

1. 환경변수 확인, Nanet 수집, PDF 파싱, 이미지 검색, 전체 payload 생성
2. 첫 Slack 게시 호출 직전 전송 단계 진입
3. payload별 게시와 고정

첫 게시 호출 전 실패한 사실을 명시적으로 확인한 경우에만 “메뉴 미전송 확인”으로 분류합니다. 전송 단계 진입 후에는 전체 작업을 자동 반복하지 않습니다.

준비 실패 여부는 예외 메시지나 기존 예외 클래스 이름으로 추정하지 않습니다. 단계 정보와 원인을 구조화해 전달합니다. 단계 정보가 없는 예상 밖 예외는 보수적으로 결과 불명으로 처리합니다.

### Nanet GET 재시도

전체 `build_messages` 또는 `run`을 반복하는 새 재시도는 추가하지 않습니다. 준비 단계에서 수행되는 기존 GET 재시도만 보완합니다.

다음 값은 **설계자가 제안하는 초기 기본값**이며 사용자 선택으로 확정된 사실이 아닙니다.

| 항목 | 제안값과 효과 |
|---|---|
| 요청당 최대 시도 | 기존 5회 유지 |
| 연결/읽기 timeout | 기존 `(10, 30)`초 유지 |
| 재시도 대기 | `5, 10, 20, 30`초 |
| 수집 누적 예산 | `NanetCollector`의 첫 GET부터 180초 |

대기를 늘리면 지속적인 연결 실패 시 약 65초에 몰려 있던 시도를 약 115초에 걸쳐 분산합니다. 더 긴 일시 장애에서 회복할 기회를 주는 대신 실패 통지가 늦어집니다. 지속적인 외부 연결 장애 자체를 해결하지는 않습니다.

예산은 목록·상세·첨부 메타데이터·PDF 다운로드와 후보 게시물 전환 사이에 공유합니다.

- 각 GET과 각 대기 시작 전에 monotonic clock으로 잔여 예산을 확인합니다.
- 대기와 요청 timeout을 잔여 예산에 맞춰 제한합니다.
- 예산이 없거나 다음 시도를 시작할 수 없는 경우 새 요청·대기·후보 처리를 시작하지 않습니다.
- `requests` timeout은 전체 작업의 엄격한 wall-clock deadline이 아닙니다. 180초 이내 종료를 보장한다고 표현하지 않습니다.
- 이미지 검색·PDF 파싱·Slack 전송은 이 수집 예산에 포함하지 않습니다. 기존 함수 제한 300초도 유지합니다.

GET 재시도 대상은 현재의 연결/읽기 오류와 HTTP 429·5xx로 제한합니다. 비재시도 HTTP 오류와 파싱 실패를 새 자동 반복 대상으로 확대하지 않습니다.

`CollectionError`에 오류 종류, HTTP 상태, 시도 횟수, 경과 시간, 예산 소진 여부를 구조화해 전달합니다. `build_messages`가 후보 오류를 `MenuParseError`로 합칠 때도 원인 정보를 보존합니다. 이 정보는 진단에 사용하며 집계된 오류를 다시 자동 재시도하는 근거로 사용하지 않습니다.

### Slack 게시와 고정

메시지를 생성하는 **`chat.postMessage`와 incoming webhook POST는 자동 재시도하지 않습니다.** 메뉴와 실패 알림에 모두 적용합니다.

공용 호출기의 기존 timeout·연결 오류·5xx 재시도 분기가 메시지 생성 요청을 반복하지 않도록 명시적으로 분리합니다. `max_attempts` 인자로 이 제한을 우회할 수도 없어야 합니다.

| 결과 | 처리 |
|---|---|
| 성공 응답과 유효한 `ts` | 게시 확인 후 고정 호출 |
| timeout·연결 오류·HTTP 5xx | 게시 결과 불명, 추가 POST 없이 중단 |
| JSON 오류·성공 응답의 `ts` 누락 | 게시 결과 불명, 추가 POST 없이 중단 |
| `internal_error`·`fatal_error` | 일부 성공 가능성이 있으므로 결과 불명 |
| HTTP 429 | `Retry-After`를 진단에 기록하되 자동 재시도하지 않음 |
| 그 밖의 API 오류 | 자동 재게시 없이 중단 |
| 게시 후 고정 실패 | 게시 확인/고정 실패로 구분하고 전체 재게시 금지 |

HTTP 429에도 자동 재시도를 하지 않는 것은 사용자가 선택한 엄격한 정책을 따르는 결정입니다.

`pins.add`도 단일 호출로 처리합니다. 고정 실패 시 확인된 `ts`를 보존하고 후속 payload 전송을 중단합니다. 운영자는 기존 메시지와 고정 상태를 확인합니다.

기존 재전송 worker의 동일 메시지 `chat.update` 및 Firestore 상태 전이는 변경하지 않습니다. 공용 호출기 변경으로 영향을 받지 않는지 회귀 검증합니다.

### 실패 알림과 재전송 안내

오류 정보에는 다음 사실을 포함합니다.

- 첫 메뉴 게시 호출 전 실패가 확인됐는지
- 게시가 확인된 payload 수와 전체 수
- 실패 단계와 payload 위치
- 확인된 메시지 `ts`
- 게시 또는 고정 결과의 불확실성

**Firebase와 CLI/GitHub Actions 모두 같은 정책을 적용합니다.** 두 경로는 공용 `app.run`을 사용합니다. 현재 formatter는 Firebase가 `retry_date`, CLI가 `retry_url`을 전달하면 재시도 UI를 만들기 때문에 호출부와 formatter의 정책을 함께 변경합니다.

| 실패 상태 | 알림과 CTA |
|---|---|
| 메뉴 게시 전 실패 확인 | 미전송 상태를 표시하고 기존 재전송 버튼 또는 재시도 URL 유지 |
| 게시 시도 이후 실패 | 재전송 버튼·재시도 URL 제거 |
| 일부 payload 게시 확인 | 게시 진행 상황 표시, 전체 재전송 CTA 제거 |
| 게시 후 고정 실패 | 기존 메시지 확인 안내, 전체 재전송 CTA 제거 |
| 단계 또는 게시 결과 불명 | 채널 확인 후 수동 복구 안내, 재전송 CTA 제거 |

결과 불명 안내 문구는 다음 의미를 전달합니다.

> 식단 게시 여부를 확인하지 못했습니다. 중복 방지를 위해 자동 재전송하지 않습니다. 채널에서 해당 날짜의 식단과 분할 메시지를 확인하고, 함수 또는 Actions 로그를 확인한 뒤 수동 복구해 주세요.

부분 게시에서는 전체 날짜 재실행을 안내하지 않습니다. 기존 게시와 누락 부분을 확인한 뒤 복구하도록 안내합니다.

실패 알림 자체가 실패하거나 결과 불명이 돼도 알림을 자동 재게시하지 않습니다. 최초 장애 원인은 보존하고 알림 실패를 로그에 별도로 남깁니다.

## 제외한 대안

- **Scheduler 재시도:** 진입 전 거부와 전송 후 실패를 안전하게 구분하지 못하므로 제외
- **최대 인스턴스 확대:** 동시 실행 범위를 넓히며 현재 선택한 준비 상태 개선에 필수적이지 않아 제외
- **전체 준비·전송 반복:** 기존 GET 재시도와 중첩되며 전송 이후 재실행 위험이 있어 제외
- **영속 전송 원장:** 실행 회차 간 중복 방지와 불확실한 게시 복구에는 별도 상태 설계가 필요하므로 제외
- **과거 메뉴 대체 게시:** 요청되지 않았고 잘못된 날짜 메뉴를 게시할 위험이 있어 제외

## 계획 깊이와 한계

새 분산 저장 상태를 추가하지 않아 Bounded 설계입니다. 그러나 공용 오류 분류와 두 진입점의 알림 동작이 연결되므로 설계 승인 후 별도 계획이 필요합니다.

구현 후 필요한 QA와 발견 사항 재검증을 수행하고, Orchestrator 수용 및 집중 커밋을 거친 뒤 독립 Reviewer가 최종 전체 변경을 검토합니다.

다음 한계는 유지됩니다.

- Scheduler는 `retry_count=0`이어도 중복 실행할 수 있습니다. 정확히 한 번 전송을 보장하지 않습니다.
- 최소 인스턴스와 직렬 실행 설정은 영속 중복 방지 장치가 아닙니다.
- 이후 발생하는 플랫폼 429는 해당 실행 유실로 이어질 수 있습니다.
- 결과 불명에서 실제 미게시된 메시지는 수동 확인 전까지 누락될 수 있습니다.
- 최소 인스턴스는 Nanet 외부 장애를 해결하지 않습니다.
- 수집 예산은 전체 함수의 엄격한 wall-clock 제한이 아닙니다.
- 로컬 변경만으로 운영 안정성 개선을 확정할 수 없습니다.

사용자 선택은 해결됐습니다. 대기 간격과 180초 예산은 설계자가 제안한 검토 대상 기본값입니다. 실행 회차 간 중복까지 차단해야 한다면 별도 Architectural 설계가 필요합니다.

## 근거와 자체 검토

저장소·운영·Git 증거는 Orchestrator brief와 앞선 읽기 전용 소스 확인에 근거합니다. 공식 사실은 다음 출처에 근거합니다.

- [Firebase Python options](https://firebase.google.com/docs/reference/functions/2nd-gen/python/firebase_functions.options): 최소 인스턴스·재시도 설정과 유휴 비용
- [Firebase 예약 함수](https://firebase.google.com/docs/functions/schedule-functions): 복수 실행 가능성
- [Slack rate limits](https://api.slack.com/apis/rate-limits): 429와 `Retry-After`
- [Slack chat.postMessage](https://api.slack.com/methods/chat.postMessage): 일부 성공 가능성이 있는 오류

자체 검토 결과:

- 플랫폼 429와 Nanet 연결 실패를 구분하고 429 실행 유실 가능성을 명시했습니다.
- Scheduler 재시도는 유지하지 않고 모든 메시지 생성 POST의 불확실한 결과 재시도를 차단했습니다.
- Firebase와 CLI 모두에 CTA 정책을 적용하며 확인된 준비 실패의 안전한 CTA는 유지했습니다.
- 원인 집계로 분류가 소실되는 문제를 구조화된 정보로 다뤘습니다.
- 새 시간값을 사용자 선택과 구분하고 예산의 한계를 명시했습니다.
- 겹치는 파일을 독립 작업으로 분해하지 않았습니다.
- 설계 초안 작성 단계에서는 코드 수정·테스트·외부 호출·배포를 하지 않았습니다. Orchestrator가 이 초안을 지정 경로에 저장했습니다. 구현은 설계 및 후속 계획 승인 전까지 보류합니다.
